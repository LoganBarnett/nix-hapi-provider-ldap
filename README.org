#+title:     nix-hapi-provider-ldap
#+language:  en

* Introduction

A standalone provider binary for [[https://github.com/LoganBarnett/nix-hapi][nix-hapi]] that reconciles entries in any RFC
4512 LDAP directory (OpenLDAP, 389 Directory Server, ApacheDS, OpenDJ).  The
provider assumes no schema.

The user side is a NixOS or nix-darwin module.  You declare the directory in
Nix, the engine diffs that declaration against the server, and the provider
applies the ~ldapadd~ / ~ldapmodify~ / ~ldapdelete~ calls that bring the server
into agreement.  No state file, no one-off scripts.  Reruns are idempotent.

Things to know up front:

1. Each LDAP server is one block under ~services.nix-hapi-ldap.servers.<name>~:
   its connection and the entries it holds.
2. The declaration is the record.  The provider owns every naming context the
   server publishes and deletes anything there that is not declared.  Two
   exceptions exist, both explicit: ~unmanagedNamingContexts~ keeps the server's
   own machinery (~cn=config~, ~cn=monitor~) out of reach, and ~ignore~ exempts
   named entries.
3. Secrets (the admin bind password, password hashes) are expressed as paths via
   ~mkManagedFromPath~ / ~mkInitialFromPath~ so they can come from ~agenix~ /
   ~sops-nix~ without entering the store.

* Installation

Add the flake input alongside nix-hapi itself:

#+begin_src nix :exports code
{
  inputs.nix-hapi.url = "github:LoganBarnett/nix-hapi";
  inputs.nix-hapi-provider-ldap.url =
    "github:LoganBarnett/nix-hapi-provider-ldap";
}
#+end_src

Then import both modules in your NixOS configuration (or the
~darwinModules.default~ pair on nix-darwin):

#+begin_src nix :exports code
{
  imports = [
    inputs.nix-hapi.nixosModules.default
    inputs.nix-hapi-provider-ldap.nixosModules.default
  ];
}
#+end_src

The provider binary is built and supervised automatically once
~services.nix-hapi.enable~ and ~services.nix-hapi-ldap.enable~ are both on.

* Usage

A minimal but realistic server looks like this.  The ~mk*~ constructors come
from ~inputs.nix-hapi.lib~.

#+begin_src nix :exports code
{ inputs, ... }: let
  inherit (inputs.nix-hapi.lib) mkManagedFromPath mkInitialFromPath;
in {
  services.nix-hapi.enable      = true;
  services.nix-hapi-ldap.enable = true;

  services.nix-hapi-ldap.servers."proton" = {
    provider = {
      url          = "ldaps://ldap.proton.lan";
      bindDn       = "cn=admin,dc=proton,dc=lan";
      bindPassword = mkManagedFromPath "/run/agenix/ldap-root-pw";
    };

    # Everything on the server is owned.  Leave the admin account alone.
    ignore = [ ''.__nixhapi.providerKey[0] == "cn=admin,dc=proton,dc=lan"'' ];

    # Top-level keys are the server's naming contexts.  Below them keys are
    # RDNs, and nesting composes the DN.
    entries."dc=proton,dc=lan" = {
      objectClass = [ "dcObject" "organization" ];
      o           = "Proton";

      entries."ou=people" = {
        objectClass = [ "organizationalUnit" ];
        entries."uid=alice" = {
          objectClass   = [ "inetOrgPerson" "posixAccount" ];
          cn            = "Alice Smith";
          sn            = "Smith";
          mail          = "alice@proton.lan";
          # Initial: written once on Add, then left alone.  Rotating the
          # file on disk does NOT re-apply; that is mkManagedFromPath.
          userPassword  = mkInitialFromPath "/run/agenix/alice-pw-hashed";
          uidNumber     = 1001;
          gidNumber     = 1001;
          homeDirectory = "/home/alice";
          # Further values of the RDN attribute are login aliases.  The
          # naming value "alice" is implied and never listed.
          uid           = [ "asmith" ];
        };
        entries."uid=bob" = {
          objectClass  = [ "inetOrgPerson" ];
          cn           = "Bob Jones";
          sn           = "Jones";
          mail         = "bob@proton.lan";
          userPassword = mkInitialFromPath "/run/agenix/bob-pw-hashed";
        };
      };

      entries."ou=groups" = {
        objectClass = [ "organizationalUnit" ];
        entries."cn=engineering" = {
          objectClass = [ "groupOfNames" ];
          description = "Engineering team";
          member      = [
            "uid=alice,ou=people,dc=proton,dc=lan"
            "uid=bob,ou=people,dc=proton,dc=lan"
          ];
        };
      };
    };
  };
}
#+end_src

The first reconcile creates the entries; later reconciles diff against the
server and apply only the deltas.  Attributes are freeform: any name passes
through, a list becomes a multi-valued attribute, numbers are sent as strings
and booleans as ~TRUE~ / ~FALSE~.  Multi-valued attributes compare as sets, so
order never matters.  Required attributes are the server's business: a missing
~sn~ fails at apply with an object class violation, after the plan has shown the
change.

** The tree

Top-level keys are the naming contexts the server publishes in its root DSE,
written as absolute DNs.  Below them keys are single RDNs and nesting is DN
composition, so the shape of the attrset is the shape of the directory.  Every
level is an ordinary entry with its own ~objectClass~, the naming context and
its OUs included, and an intermediate node is declared like any other.
Removing a node from the declaration deletes it and everything beneath it,
deepest first.  Declaring one DN twice, under any spelling of case or spacing,
is an evaluation error that names both declarations.

#+begin_src nix :exports code
services.nix-hapi-ldap.servers."proton".entries."dc=proton,dc=lan".entries = {
  "ou=services" = {
    objectClass = [ "organizationalUnit" ];
    entries."ou=web" = {
      objectClass = [ "organizationalUnit" ];
      entries."cn=gitea".objectClass = [ "applicationProcess" ];
    };
  };
  "cn=replicator" = {
    objectClass  = [ "simpleSecurityObject" "organizationalRole" ];
    userPassword = mkManagedFromPath "/run/agenix/replicator-pw";
  };
};
#+end_src

** Provider connectivity

- ~url~ :: ~ldap://~, ~ldaps://~ or ~ldapi://~.  Use TLS off loopback; the bind
  password travels in cleartext on plain ~ldap://~.
- ~bindDn~ :: the account the reconciler binds as.  It needs write access to
  every managed naming context.
- ~bindPassword~ :: almost always ~mkManagedFromPath~.  Runbook output scrubs it
  to ~***~.

All three are ~value~-typed, so ~mkManagedFromEnv~ or a bare string work too.
Beside ~provider~, ~unmanagedNamingContexts~ lists the naming contexts the
provider never reads or writes.  It defaults to OpenLDAP's ~cn=config~ and
~cn=monitor~.

** Renaming entries

Entries change RDN over time.  The engine's ~providerKey~ history tracks that
declaratively: the attrset key composes the current DN, and
~__nixhapi.providerKey~ lists it first followed by every prior DN.  The next
reconcile finds the live entry under a prior DN, emits a ~Rename~, and the
provider issues an LDAP ~modifyDN~; attributes you do not redeclare are
preserved.  Keep the history entries.  They are declared state, not something to
prune after the first apply.

#+begin_src nix :exports code
entries."dc=proton,dc=lan".entries."ou=people".entries."uid=alicia" = {
  objectClass = [ "inetOrgPerson" ];
  cn          = "Alice Smith";
  sn          = "Smith";
  __nixhapi.providerKey = [
    "uid=alicia,ou=people,dc=proton,dc=lan"   # head: the composed DN
    "uid=alice,ou=people,dc=proton,dc=lan"    # prior DN
  ];
};
#+end_src

The provider renames leaf entries only, the one form every server supports.
Changing a parent's key therefore means:

1. The parent is recreated.  It carries no history.
2. Every child's DN changes with it, since nesting composes DNs.
3. A child that carries the rename is moved, attributes intact.
4. A child without history is recreated from its declared attributes.

Nothing is left behind.  A small function applies the history to a whole
subtree:

#+begin_src nix :exports code
let
  movedFrom = oldParent: lib.mapAttrs (rdn: body: body // {
    __nixhapi.providerKey = [
      "${rdn},ou=staff,dc=proton,dc=lan"
      "${rdn},${oldParent}"
    ];
  });
in {
  entries."dc=proton,dc=lan".entries."ou=staff" = {
    objectClass = [ "organizationalUnit" ];
    entries = movedFrom "ou=people,dc=proton,dc=lan" people;
  };
}
#+end_src

** Exceptions

Everything in a managed naming context that Nix does not declare is deleted on
reconcile.  ~ignore~ takes jq expressions run against each live entry; a truthy
result exempts it from deletion.  Predicates only suppress deletes; an ignored
DN that is also declared is diffed and modified as usual.  For whole trees the
server keeps for itself, use ~unmanagedNamingContexts~ instead.

#+begin_src nix :exports code
services.nix-hapi-ldap.servers."proton".ignore = [
  # The admin account the provider binds as.
  ''.__nixhapi.providerKey[0] == "cn=admin,dc=proton,dc=lan"''
  # Anything tagged with a "system" description.
  ''(.description // "") | test("^system:")''
];
#+end_src

* Gotchas and Tradeoffs

- *The first plan against an existing directory is a reckoning.*  Every entry in
  a managed naming context that is not declared is listed as a delete.  Declare
  it, ignore it, or let it go.
- *Plain key renames are delete + recreate.*  Changing an entry key without
  listing the prior DN in ~providerKey~ produces an Add and a Delete.  See
  [[Renaming entries]].
- *DN-valued attributes do not follow renames.*  ~member~, ~manager~ and
  ~seeAlso~ hold DN strings that neither Nix nor the server rewrites.  Compose
  them from the same values the keys are built from.
- *DN matching is string-exact.*  Declare a DN exactly as the server stores it;
  a pre-existing entry with different casing plans as delete + add.
  Multi-valued RDNs and escaped commas are unsupported.
- *The server enforces schema.*  A missing required attribute or a zero-member
  ~groupOfNames~ fails at apply (result 65); changing a structural class in
  place is refused (result 69).
- *Waves follow ~derivedFrom~ and ~dependsOn~, not DN depth.*  A parent whose
  attribute is derived can be scheduled after its child.
- *~mkInitial~ vs ~mkManaged~ for passwords.*  ~mkInitial~ writes once;
  ~mkManaged~ enforces the hash every reconcile and clobbers out-of-band
  changes.  Pick deliberately.
- *One TCP connection per reconcile.*  Each naming context is read in one
  search, in parallel; applies run sequentially.

* How to Exercise Various Features

- *Plan without applying.*  The engine produces a runbook of LDIF
  bodies before touching the directory.  Pipe the evaluated
  desired-state JSON into ~nix-hapi plan~ to inspect the scrubbed
  ~ldapmodify~ commands; the NixOS / nix-darwin modules only wire up an
  ~apply~ unit, so plan is a manual CLI step.
- *Mixed-source secrets.*  Combine ~mkManagedFromPath~ for the bind
  password with ~mkInitialFromPath~ for per-user hashes when you want
  server-side credential rotation to win over Nix redeployment.
- *Several servers per host.*  Add as many
  ~services.nix-hapi-ldap.servers.<name>~ blocks as you have directories;
  each gets its own provider subprocess and connection.
